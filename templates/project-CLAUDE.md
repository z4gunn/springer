# Project - Springer Agent Rules

This file is the operative ruleset for the AI agents building this application. It loads every session and OVERRIDES default behavior. This project was instantiated from Springer, an AI software development team built as a library of Claude Code agents and skills. The agents in `.claude/agents/` and the skills in `.claude/skills/` drive the full lifecycle, from idea to production, and you the human enter only at deliberate checkpoints.

## How to start

Run the `spgr-run-harness` skill in the main session with a problem statement that carries a `profile:` line, and optionally an `autonomy:` line. The harness loops the Orchestrator (`spgr-agent-orchestrator`), which returns routing only, and the domain agents it routes, and pauses only at the gates your autonomy level fires. You can also invoke one agent for one phase by hand, for example `spgr-agent-discovery` to start research or `spgr-agent-architect` to produce architecture options.

## Core Design Principles

These constraints shape every agent and are non-negotiable.

1. Architecture first. No development begins until you approve the architecture. The Architect agent proposes at least two distinct options with full tradeoffs. It does not select. You select. Once approved, the gate-list decisions are immutable: the data model and tenancy boundary, the auth model, billing, a vendor or sub-processor, anything irreversible. A developer agent that cannot satisfy a requirement within those escalates rather than deviating. Every other architecture clause (a derivation rule, a prompt, a layout, a library inside the stack) is amended by the implementing agent as one decision-log line with the PR number, never a versioned ADR or a gate.
2. Minimal human-in-the-loop. The only required gates are architecture approval, design-direction selection, pull-request merge, a vertical security or compliance flag, and a scope change. Work between these gates flows agent to agent. The run's autonomy level decides how many sittings these take. Under `standard`, you answer the PRD, every question the run needs from you, the architecture option, and the design direction in one direction review, and a reversible decision inside the profile is taken by default and listed for you at the next gate instead of interrupting you. A gate holds only the work that depends on it, so the rest keeps running while you are away. Every question or next step for you is asked through the interactive question tool (`AskUserQuestion`), never left as prose at the end of a turn: each option carries its consequence, the recommended one comes first, and you can always type another answer. A turn never ends idle with an open question in the chat body. The pull-request gate fires once per batch or per page, not per story. Under `autopilot`, on any profile, a PR that `pr-risk.py` scores low or medium merges on its own once the reviewer approves, the receipts verify, and CI is green. A high-risk PR (auth, the data model or a destructive migration, billing, a new vendor, CI and infra, secrets, an open Critical or High finding, or a placeholder) waits for you and holds only the work that depends on it. A production deploy always waits for you.
3. Structured artifact contracts. Every handoff is a typed artifact with enumerated required fields, per-section rationale, explicit confidence signals (confirmed, proposed, needs-human-input), and a versioned schema. The receiving agent validates the artifact before acting on it.
4. Escalation is not failure. An agent that refuses to proceed on incomplete or contradictory input, and returns a precise list of what is missing, is doing its job. Agents do not fill gaps with assumptions. A default taken on a reversible decision is not a gap filled silently: it is named in the defaults ledger and reviewed at the next gate.
5. Vertical agents are consulted by diff and budgeted. Cross-cutting concerns (auth, security, compliance, observability, performance, accessibility) are not bound to a single phase, and a vertical is dispatched when a diff touches its paths, at most two per pull request. Its sign-off gates the architecture artifacts it owns. On a pull request it blocks only on a Critical finding in its own domain, and every other finding is a follow-up issue.
6. Design agents receive maximum creative latitude. They receive the problem and the personas, not wireframes, and produce multiple distinct directions. You select one direction. The agent then executes that direction with precision. When a reference implementation exists, one direction is the reference carried forward.
7. The product check is the definition of done. A user-visible story is done when the real product, on real inputs, shows what you asked for: the checks in `runs/_product-check.json` run at every Check, their results are the one figure the harness is measured by, and a story without a passing check is unverified, not done. On `small`, `saas`, and `mobile` the first batch is a walking skeleton of the primary flow, deployed before any other story is built.

## Run profile

Every run declares a profile on a `profile:` line in its problem statement: `brochure` (a static site or landing page, no backend), `small` (one service or app with a UI, user accounts allowed, no tenancy and no billing), `saas` (charges money or serves more than one tenant), `mobile` (store-distributed), or `api` (headless: a backend API, an integration service, a CLI, a library). Pick it with four questions, first yes wins: in an app store, `mobile`. Charges money or multi-tenant, `saas`. Has a user interface, `small`, or `brochure` when it has no backend either. Otherwise `api`. A `mobile` run may add `size: small` for a utility app with no backend of its own, which keeps the store lifecycle at `small` ceremony. The profile scales the lifecycle: which phases run, how many stories the backlog may hold, whether an ADR set or a single architecture note is written, how criteria are written, and what one pull request covers. The table is in `.claude/references/pdca-harness.md` under Run profiles. Default profile for this project: `saas`. A statement with no profile line is not an error: the harness answers the four questions itself, records the choice as a default, and you confirm or overturn it at the first gate. Changing a run's profile after it opens is a scope-change gate.

A run may also declare an autonomy level on an `autonomy:` line: `supervised` (opt-in: every gate is its own sitting and nothing is taken by default), `standard` (the default on every profile), or `autopilot` (any profile: one direction review, PRs merged by risk, and the defaults listed in the completion notice). Defaults taken are one line each in `runs/<run-id>/pending-defaults.md`. A missing fact is never invented: it ships as a visible `TODO(DEF-<n>)` placeholder, and a placeholder blocks auto-merge. The autonomy table is in `.claude/references/pdca-harness.md`. To leave a run going while you are away, start it with `autonomy: autopilot`, answer the direction review, then run `python3 .claude/skills/spgr-run-harness/scripts/run-unattended.py <run-id>` from a terminal. It runs fresh sessions back to back, sleeps through usage limits, and posts to the Slack webhook in `SPRINGER_SLACK_WEBHOOK_URL` in `.env` when the run completes or needs you.

A run may also declare a `lane:` line. With none, the harness opens `polish` when the product already runs where a user can reach it and `build` otherwise. Default lane for this project: `build`. `build` runs the profile's lifecycle, and once its walking skeleton is deployed every later story runs at polish ceremony unless it touches the gate list. `polish` is for a product that already exists: one issue in your own words becomes one pull request, checked by code review, the verticals the diff touches, and the product check, with no PRD, story, criteria, or ADR artifact unless the change is on the gate list. A `reference:` line names a POC, prototype, or earlier version the run treats as its spec: its features are inventoried and transcribed into the backlog, its look is one of the design directions, and parity with it is in the definition of done. Both are in `.claude/references/pdca-harness.md` under Lanes and Reference implementation.

## Where things live

This project directory is the build target. Source code is written into the project tree at the repository root, and the file-writing tooling refuses to write outside it.

- `runs/<run-id>/` is the artifact store. Each run holds `artifacts/`, `archive/`, `escalations/`, `checkpoints/`, and `consultations/`. Every typed artifact (PRD, ADRs, ERD, test plan, and so on) lives here, and it stays the source of truth.
- `docs/` holds human-readable, regenerable copies of the early-phase artifacts: the high-level PRD, ADRs, architecture diagrams (Mermaid with best-effort excalidraw and PNG), user-story summaries, and the discovery write-ups, plus the clickable HTML design-direction mockups under `docs/design/` and the high-fidelity comps with their screenshot matrix under `docs/design/comps/`. When the impeccable engine is installed on the machine, the design hook in `.claude/settings.json` runs its detector after every UI edit and on Stop and surfaces the findings to the editing agent. Its cache lives in `.impeccable/` and is ignored by git. The harness renders them at a human checkpoint for the artifacts that checkpoint reads, so you review readable docs instead of raw JSON. Between checkpoints a doc may be stale and says so in its header. They are derived from the artifacts in `runs/`, so ask for `spgr-render-doc` rather than hand-editing.
- `runs/<run-id>/run-brief.json` is the run's compact projection: profile, flags, your rulings as one line each, and the operative artifact list. `runs/<run-id>/pending-foldins.md` holds one line per correction to a confirmed artifact and is applied in the cycle it is opened or deferred.
- Application source code, configuration, tests, and CI live in the project tree, the same place any other repo keeps them.
- `schemas/` holds the JSON Schemas that artifacts validate against.
- `runs/_product-check.json` lists the product checks, and `tests/fixtures/real/` holds the real, anonymized inputs they run on. Your own sample files are the first fixtures.
- `.claude/references/` holds the shared cross-skill references, cited by repo-relative path.

## Generated Code Standards

Any JavaScript-runtime stack this project selects MUST be TypeScript. Plain JavaScript is not permitted for new source. All generated TypeScript follows `.claude/references/typescript-standards.md`, the single source of truth for the tooling baseline (gts), compiler strictness, lint rules, and format rules. An agent that cannot satisfy a requirement in TypeScript within the approved architecture escalates rather than falling back to plain JavaScript. Other languages (for example Python, Go, Swift, Kotlin) keep their stack-default tooling and are unaffected by this rule.

## Git conventions

This project follows a trunk-based workflow: `main` is always deployable, every change lands through a short-lived branch and a reviewed pull request, and `main` is protected against direct pushes. The full model, including branch naming, the merge bar, and the release and hotfix flow, is defined in `.claude/references/git-workflow.md`.

- Use conventional commit messages, scoped by what changed (for example `feat(api): add subscription endpoint`, `chore(ci): add typecheck stage`).
- One logical change per commit. Lint, format, and the type checker pass before every commit. The hook chain is never bypassed, and a PreToolUse hook refuses `--no-verify`. Another refuses an agent edit or shell write to an existing lint, type, test-runner, or coverage config, a harness hook, a real fixture, a unit's receipts, or `runs/_risk.json`. A change the story needs is a ruling the harness records in `runs/_config-unlock.json`. Evidence is a receipt from `receipt.py`, never a pasted claim, and a test run that ran nothing is a failure.
- Every changed line traces to the story or the finding that asked for it. Adjacent code, comments, and formatting are left alone, and pre-existing dead code is reported, not deleted.
- Never commit secrets or `.env`.
- At a `pr-merge` gate the harness publishes automatically: once all automated sign-offs pass it commits, pushes the branch to origin, and opens a PR via `spgr-create-pr`, then pauses at the human merge checkpoint carrying the PR URL. It merges the PR itself when `pr-risk.py` scores it low or medium under `autopilot` or `auto_merge_on_green`, on any profile, and it uses a local-only unpushed branch only when a human explicitly asks. See the pr-merge gate rule in `.claude/references/pdca-harness.md`.
